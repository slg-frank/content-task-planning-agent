# 01 项目需求

## 用户与目标

目标用户为内容运营人员。系统最终需要根据主题、预算和截止时间生成可执行的内容活动方案。

## 当前阶段范围

阶段 12 对阶段 01～11 的交付物执行密钥、隐私、本机路径、忽略规则、依赖、许可证和干净环境检查。只有交付测试与全量回归通过后，才允许提交并推送到目标 GitHub 仓库。

## 输入约定

- `topic`：必填，去除首尾空白后不得为空，最长 500 个字符。
- `budget`：必填，必须是大于或等于 0 的有限数值，内部使用 `Decimal`。
- `deadline`：必填，必须是带 UTC 偏移或 `Z` 后缀的 ISO 8601 时间，并晚于任务开始时间。
- `task_id`：可选；未提供时生成 UUID，提供时只允许字母、数字、点、下划线和连字符，最长 128 个字符。
- `model_mode`：可选，值为 `mock` 或 `real`，默认 `mock`。
- `failure_injection`：可选，必须是对象，仅用于后续测试场景。

输入无效时必须返回稳定错误码、空步骤和零费用，不能进入工具或 Agent 执行流程。

## 阶段 03 工具约定

- 素材检索从 `data/materials.json` 返回确定性的合成素材。
- 脚本生成根据主题、素材和 `standard`/`economy` 方案生成确定性脚本。
- 成本估算从费用表计算方案预计总费用，标准方案为 12，经济方案为 8。
- 方案保存只允许写入经过批准的运行输出根目录。
- 工具调用费用和方案预计费用分别记录，不能混为一项。
- 测试可为每个工具注入确定次数的失败；默认失败调用不计费。
- 部分成功结果必须设置 `partial_success` 并说明缺少或忽略的内容。

## 阶段 04 状态与 Trace 约定

- 步骤必须按允许的状态迁移，禁止直接将失败步骤改成成功。
- 每个结束的工具调用只累计一次费用、耗时和调用次数。
- 失败步骤如需重试，必须显式回到 `running` 后再记录新的结果。
- 执行状态以 JSON 文件持久化，成功结果必须能跨进程重新读取。
- Trace 使用按任务划分的 JSONL 文件，记录步骤编号、动作、参数、结果摘要、状态、累计费用、预计费用、累计耗时、后续动作和简要决策依据。
- Trace 必须递归隐藏敏感字段，并替换从敏感环境变量泄漏到普通文本中的值。

## 阶段 05 模型动作约定

- 模型只能返回 `call_tool`、`select_alternative`、`stop` 或 `complete`。
- 工具白名单仅包含素材检索、脚本生成、成本估算和方案保存。
- 每种工具具有独立的必填参数、可选参数和类型约束，未知参数被拒绝。
- `select_alternative` 只能指定 `plan_profile`；停止和完成动作不得携带工具或参数。
- 决策依据必须是 1～500 个字符的可审计摘要，不记录内部思维过程。
- 模型适配器只选择动作，不直接执行工具；非法输出在执行边界之前被拒绝。
- Mock 模式不需要密钥，真实模式需要显式配置 `OPENAI_API_KEY` 和 `OPENAI_MODEL`。

## 阶段 06 ReAct 循环约定

- 每轮必须依次完成模型选动作、工具执行、观察记录和下一轮模型决策。
- 工具只能由经过校验的 `call_tool` 动作触发，测试不得直接代替循环串行调用工具。
- 每次工具调用后立即更新步骤状态、累计费用、累计耗时、工具调用次数、状态文件和 Trace。
- 成本估算成功后将预计总费用同步到执行状态。
- `complete` 只有在四个必要步骤均成功时才成立；提前完成返回未完成。
- `max_steps` 限制模型决策次数，`max_tool_calls` 限制工具调用次数。
- 达到任一上限时必须停止并返回 `step_limit_reached` 或 `tool_call_limit_reached`。

## 阶段 07 预算与截止时间约定

- 成本估算同时返回方案预计费用和预计执行时长。
- 标准方案预计费用为 12、预计时长为 120 秒；经济方案为 8、60 秒。
- Agent 上下文必须包含预算缺口、可用时长、预计总耗时和截止时间缺口。
- 改选方案后，旧估算只能作为历史结果保留，当前方案必须重新估算。
- 保存前必须验证必要步骤成功、当前方案已估算、费用不超预算、预计耗时不超截止时间、保存内容方案类型一致。
- 没有可行方案时返回未完成，并保留实际预算或时间缺口。

## 阶段 08 失败与部分成功约定

- 所有工具失败结果必须包含错误码、摘要和 `retryable` 标志。
- 一次性测试故障属于可重试错误；参数、配置和确定性业务错误默认不可重试。
- 未预期的工具异常必须转换为不可重试的结构化失败，步骤状态落为 `failed`。
- 模型只能在执行步数和工具调用次数上限内重试。
- 后续失败不得清除此前成功步骤的结果。
- 部分成功保持 `success=true` 和 `partial_success=true`，后续步骤只能使用返回的真实成功数据。
- 每次失败和重试均写入独立 Trace 记录，包含错误摘要、后续动作和简要依据。

## 阶段 09 幂等性约定

- 任务身份由 `task_id` 和关键输入指纹共同确定。
- 指纹包含主题、规范化预算和转换到 UTC 的截止时间，不包含密钥或测试失败注入配置。
- 已完成任务重复执行时直接返回原结果，不调用模型、工具，不重复计费、保存或追加 Trace。
- 相同任务 ID 但主题、预算或截止时间变化时返回 `conflict` 和 `task_input_conflict`，不得覆盖原状态。
- 数值等价的预算和代表同一时刻的不同时区时间不得误报冲突。
- 未完成任务重复执行时默认返回原状态且不擅自续跑；失败步骤续跑作为后续加分能力。

## 阶段 10 CLI 约定

- `run` 命令同时支持直接参数和 UTF-8 JSON 对象输入；直接参数覆盖 JSON 中的同名任务字段。
- 可选择 `mock` 或 `real` 模式，并可指定任务 ID、运行根目录、状态目录、Trace 目录、JSON 结果文件和两类执行上限。
- 标准输出只包含完整、可解析的 JSON 最终结果；人类可读摘要写入标准错误。
- 稳定退出码为：完成 `0`、输入错误 `2`、未完成或冲突 `3`、模型配置或系统错误 `4`。
- 输入错误不得创建状态、Trace、方案或产生工具费用。
- CLI Mock 必须读取实际状态和最后观察选择下一动作，而不是为每个场景伪造固定最终输出。
- 真实模式缺少配置时必须明确失败，不得静默回退 Mock。
- 相同任务 ID 和相同关键输入从 CLI 重复执行仍必须保持文件、费用和调用次数不变。

## 阶段 11 验收材料约定

- 五组强制场景必须由生成脚本实际调用 CLI，不能手写最终状态或伪造 Trace。
- 每组至少保留输入、CLI 输出、运行记录和 `trace.jsonl`；成功场景同时保留状态和方案。
- 输入校验失败不创建业务 Trace，因此其 `trace.jsonl` 必须为空，运行记录必须明确说明没有运行目录和收费工具调用。
- 运行记录包含命令、退出码、标准错误摘要、生成时间和产物事实；临时绝对路径允许做范围明确的可移植归一化。
- 工具失败 Trace 必须显示失败观察引发重试；预算 Trace 必须显示预算缺口引发改选方案和重新估算。
- 重复执行材料必须同时保存两次输出，并证明状态、方案和 Trace 在第二次调用前后均未变化。
- `acceptance-matrix.json` 将每个强制验收点映射到至少一个实际场景。
- 五份文档必须如实引用存在的材料、测试结果、实际投入时间、未完成内容和已知限制。

## 阶段 12 交付约定

- 仓库不得包含真实 API 密钥、令牌、私钥、个人隐私数据或本机绝对路径。
- `.env`、虚拟环境、缓存、构建目录和 `runtime/` 必须被忽略且不得进入提交。
- 包元数据必须声明 Python 版本和真实运行依赖，不能依赖开发机预装包。
- 必须在新的隔离虚拟环境按 README 安装依赖、安装项目、运行 CLI 冒烟测试和全量测试。
- 必须记录依赖版本与许可证；项目自身没有许可证时应明确说明，不得擅自假定开源授权。
- 交付测试、全量回归和 Git 工作区检查全部成功后才能创建提交。
- 目标仓库为 `https://github.com/slg-frank/content-task-planning-agent`，提交成功后记录最终 commit SHA。

## 总体验收范围

后续阶段必须覆盖正常完成、缺少输入、工具失败、预算超限和重复执行，并通过实际输出与 Trace 证明动态决策。
