# 02 方案设计

## 技术选择

- Python 3.11+
- CLI 运行方式
- pytest 测试框架
- `src` 目录布局
- 后续使用本地 JSON 保存状态、方案和 Trace

## 当前阶段设计

阶段 01 提供可安装的 Python 包、最小 CLI 和测试入口。阶段 02 使用标准库数据类和字符串枚举定义领域模型，并使用 `Decimal` 避免费用计算中的浮点误差。时间输入必须带时区，测试可以注入固定的当前时间以保证可复现。

校验器一次收集全部可识别的字段错误，返回结构化 `ValidationResult`。无效结果在类型层面默认具有空步骤和零费用，从而阻止无效输入产生业务副作用。工具、模型适配器、状态存储和 ReAct 循环将在对应阶段设计和实现。

## 设计取舍

优先选择轻量 CLI 和本地依赖，以便评审人员快速安装、运行和复现测试结果。

阶段 02 不引入额外校验框架，避免在简单领域模型上增加依赖；稳定错误码与序列化方法为后续 CLI、状态文件和 Trace 提供统一边界。

## 阶段 03 工具设计

四类业务工具均使用结构化请求和统一 `ToolResult`，可以脱离 Agent 独立调用。工具从版本化 JSON 表加载合成素材、调用费用、模拟耗时和方案费用，确保测试可复现。

`FailureInjector` 按工具名称和失败次数维护一次性状态。共享同一实例时，可以稳定模拟“第一次失败、下一次成功”，为后续 Agent 重规划测试提供基础。部分成功与完全失败分开表达：部分成功保持 `success=true`，同时设置 `partial_success=true` 和警告；完全失败具有稳定错误码、零费用且没有成功标记。

方案保存工具默认写入项目 `runtime/`，调用方只能选择批准根目录下的子目录。测试通过临时批准根目录验证实际文件写入，不允许路径逃逸。

## 阶段 04 状态与 Trace 设计

`ExecutionState` 保存任务级状态、步骤、累计费用、预计费用、累计耗时和工具调用次数。`transition_step` 使用显式迁移表保护步骤生命周期，并在工具调用结束时一次性更新累计值。失败步骤不能直接改成成功，重试必须经过新的 `running` 状态。

`StateStore` 按任务 ID 保存独立 JSON 文件，写入时先生成临时文件再替换目标文件，避免正常写入过程中留下半文件。加载时恢复枚举、`Decimal`、步骤和工具结果。

`TraceRecorder` 以 JSONL 顺序追加记录，重新创建实例后仍可读取历史记录。脱敏同时覆盖敏感键和敏感环境变量值，并对嵌套对象、数组和普通文本递归处理。简要决策依据限制为 500 个字符，不记录模型内部思维过程。

## 阶段 05 模型适配设计

`ModelAdapter` 协议统一离线 Mock 和真实模型的 `choose_action` 接口。`ModelContext` 只传递任务、当前执行状态、最后一次工具观察和工具白名单；`ModelAction` 只表示下一动作，不承担工具执行职责。

离线 `MockModelAdapter` 按预设动作序列返回结果，每个动作仍经过与真实模型相同的本地校验，因此可复现流程但不能证明真实模型决策质量。`OpenAIModelAdapter` 使用 Responses API 的严格 JSON Schema 约束顶层输出，再由应用校验动作、工具白名单、参数白名单和类型。实现依据为 [OpenAI Structured Outputs 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)。

真实模式从环境读取密钥和模型名称，不提供硬编码密钥，也不在配置缺失时静默降级。提供者拒绝、空输出、无效 JSON 和非法参数均转换成明确异常，未经验证的内容不会交给工具层。

## 阶段 06 ReAct 循环设计

`AgentRunner` 将阶段 02～05 的组件组合为闭环。模型收到任务、当前执行状态和最后一次观察；合法的工具动作由 `LocalToolExecutor` 映射到四类业务工具；工具结果通过状态机记账并持久化，同时写入 Trace，随后作为下一轮 `last_observation` 反馈给模型。

执行骨架预先定义四个必要步骤，但步骤是否执行、何时停止以及观察后的下一动作由模型动作决定。`complete` 会检查四个步骤的实际成功状态，不能用模型声明覆盖失败或未执行状态。成本估算的预计总费用与工具调用的已发生费用分别保留。

循环维护独立的模型决策次数和工具调用次数。到达配置上限后保存当前状态并返回明确未完成原因。阶段 06 已证明不同工具观察可以产生不同后续动作；预算和时间约束的完整重规划策略留在阶段 07。

## 阶段 07 约束与重规划设计

成本估算工具从费用表和耗时表同时返回预计总费用与预计总时长。`AgentRunner` 根据任务开始时间计算可用秒数，将当前工具耗时与方案预计时长相加，形成预算缺口和截止时间缺口，并将约束快照加入每次模型上下文和工具观察。

模型选择替代方案时，旧成本步骤和结果保持成功并留在状态与 Trace 中，但当前估算标识被清空。只有再次执行成本估算并使 `estimated_plan_profile` 与所选方案一致，保存保护才会放行。重复成本估算使用新的步骤保存结果，避免覆盖首次 12 单位的证据。

保存保护独立于模型：它检查素材、脚本和估算依赖，重新估算状态、预算、截止时间以及保存内容中的方案类型。约束不满足时不调用保存工具、不产生保存费用，记录 `blocked` Trace，并将具体阻塞原因反馈给模型继续调整或停止。

## 阶段 08 失败恢复设计

统一 `ToolResult` 增加 `retryable`。测试注入故障标记为可重试，其他确定性失败默认不可重试。Agent 将失败结果正常写入步骤、累计调用次数、状态文件和 Trace，再把完整观察交给下一轮模型；模型可以重试、调整参数或停止，但仍受双重执行上限约束。

工具执行器抛出的未预期异常不会使步骤停留在 `running`。Agent 将其转换为 `unexpected_tool_exception`、标记不可重试并迁移到 `failed`，同时只记录异常类型而不暴露内部敏感信息。

部分成功按成功步骤保存，但 `partial_success`、警告、真实结果数和缺失数均保留。后续 Mock 策略从状态中的真实素材列表构造脚本参数，因此缺失素材不会被伪造。成功素材步骤在脚本失败或重试期间不重新执行、不丢失。

## 阶段 09 幂等性设计

首次运行使用规范化主题、预算和 UTC 截止时间生成 SHA-256 指纹，并与任务状态一起保存。`AgentRunner.run` 在调用时首先查询 `StateStore`：指纹一致时直接从状态重建结果，指纹不一致时返回冲突。该检查发生在读取时钟、调用模型或调用工具之前。

完成任务的缓存返回不会重新保存状态，因此状态 JSON、Trace JSONL 和方案 JSON 的内容及修改时间均保持不变。输入冲突同样只读原状态。预算使用 `Decimal.normalize` 后的普通十进制文本，截止时间转换 UTC，避免 `20.00`/`20` 或等价时区表示造成假冲突。

未完成任务当前采用安全默认值：返回原状态，不自动续跑。这满足重复执行不产生副作用的核心要求；如果后续实现显式续跑，将只恢复未成功步骤并增加单独的用户选择和测试。

## 阶段 10 CLI 集成设计

CLI 使用 `run` 子命令统一直接参数与 JSON 文件输入。合并后仍调用阶段 02 的同一校验器，避免命令行和库调用形成两套业务规则；执行目录和上限属于运行配置，不进入任务指纹。输入在创建 `StateStore`、`TraceRecorder` 或工具执行器前完成校验，因此缺预算、缺截止时间等错误没有运行副作用。

默认 `PlanningMockModelAdapter` 与测试使用的脚本化 `MockModelAdapter` 分开。前者每轮读取真实执行状态、约束和最后工具观察，依次检索素材、生成脚本、估算成本、按缺口选择经济方案、重新估算、保存并完成；可重试失败会使用同一参数重试，不可重试失败安全停止。脚本化 Mock 保留给更低层的精确动作边界测试。两者都经过同一个动作解析和工具白名单。

完整 JSON 写入标准输出，可选同步写入 `json_output` 文件；摘要写入标准错误，避免破坏管道解析。退出码固定为 `0/2/3/4`，分别表示完成、输入错误、未完成或冲突、系统或配置错误。真实模型由显式 `real` 模式选择，配置不足返回系统配置错误，不进行隐式模式切换。

## 阶段 11 验收材料设计

`examples/generate_stage_11_examples.py` 使用临时隔离运行目录，通过 `python -m content_agent.cli run` 子进程生成五组材料。脚本解析真实 stdout、保留 stderr 与退出码，并从真实运行目录复制状态、保存方案和 JSONL Trace。生成过程不直接调用工具或构造 Agent 最终状态，因此材料经过与用户运行相同的 CLI 边界。

为避免提交本机临时目录，生成器只将输入文件和运行根目录的绝对路径替换为 `input.json` 与 `${RUNTIME_ROOT}`；该规则写入每组 `run-record.json`。业务字段、费用、步骤、决策依据、Trace 时间和工具结果不做语义修改。缺输入场景因校验前置而没有运行目录，生成器保留空 Trace 文件并记录 `trace_created=false`，使“没有工具调用”本身成为可测试证据。

重复执行场景在同一隔离目录连续调用两次 CLI，调用间记录状态、方案和 Trace 的 SHA-256 与纳秒修改时间，第二次调用后逐项比较。`tests/test_acceptance.py` 不重新伪造场景，而是校验已保存材料的结构、业务一致性、动态决策证据、幂等事实、文档引用和验收矩阵。

## 阶段 12 交付设计

`tests/test_delivery.py` 扫描所有可交付文本文件中的常见密钥、私钥标记和 Windows 本机绝对路径，并通过 `git check-ignore --no-index` 验证 `.env`、虚拟环境、pytest 缓存、Python 字节码和运行状态均受忽略规则保护。测试同时核对必需代码、数据、文档、五组示例、阶段记录、JSON 可解析性和 README 交付命令。

包元数据将 OpenAI SDK 明确列入运行依赖，使 `pip install -e .` 不再依赖开发机偶然安装的 SDK。交付验证使用新建的 `.venv`，依次安装 `requirements.txt`、可编辑项目，执行版本命令、离线 CLI 正常场景、阶段 12 专项测试和全量回归。

GitHub 仓库保持空仓库初始状态，不由 GitHub 自动生成 README、忽略文件或许可证，避免与本地权威文件冲突。项目未获得所有者的许可证选择，因此文档明确保留默认版权状态；这比擅自添加 MIT 或 Apache 许可证更符合交付边界。
