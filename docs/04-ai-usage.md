# 04 AI 辅助使用说明

## 阶段 01～05 使用范围

AI 用于梳理原始需求、制定分阶段计划，并辅助生成项目骨架、CLI 基线、领域模型、输入校验、合成数据、本地业务工具、状态持久化、Trace 脱敏、模型动作边界和阶段测试。

阶段 05 的 OpenAI 适配方式依据官方 Structured Outputs 文档核对；实际测试使用注入的假客户端，不发送网络请求、不使用真实密钥，也不把 Mock 测试结果描述为真实模型效果。

阶段 06 使用可复现的 Mock 动作和观察驱动策略验证 ReAct 工程闭环。Mock 能证明动作、工具、状态和 Trace 的连接关系，但仍不证明真实模型在开放输入下的规划质量。

阶段 07 使用读取约束快照的确定性 Mock 策略验证预算和时间观察确实改变后续动作。预算、截止时间和保存条件同时由确定性代码强制执行，避免仅依赖模型文本判断。

阶段 08 使用读取 `retryable`、错误码和部分成功数据的确定性 Mock 策略验证失败后的动作变化。测试证明工程状态和恢复路径，不把预设 Mock 的恢复判断描述为真实模型能力。

阶段 09 的幂等判断完全由确定性代码和持久化状态完成，不依赖模型判断。重复运行测试复用已经耗尽的 Mock 动作序列，以证明第二次运行确实没有调用模型。

阶段 10 使用观察驱动的确定性 CLI Mock，将此前组件组合为可复制运行的端到端入口。它根据状态中的成功步骤、约束缺口、`retryable` 和真实工具结果选择动作，而不是直接返回预设最终 JSON；这仍然只是离线工程验证，不能外推为真实模型效果。CLI 真实模式沿用阶段 05 的适配器和显式配置边界。

阶段 11 由 AI 辅助设计验收矩阵、生成脚本、自动测试和文档交叉引用。五组业务结果不是 AI 手写样例：生成脚本通过真实 CLI 子进程产生 stdout、stderr、状态、方案和 Trace。AI 只对临时绝对路径执行声明过的可移植归一化，并通过验收测试检查记录内部一致性。

阶段 12 由 AI 辅助执行交付清单、编写安全与完整性测试、核对依赖元数据和许可证信息，并在隔离环境复现安装和测试。GitHub 仓库名称与公开属性由用户明确确认；AI 不创建密钥、不选择项目法律许可证，也不在检查失败时推送代码。

## 人工修改与验证

所有生成内容均需通过阶段测试和全量回归测试验证。测试失败时必须修复后重新运行，不能用文字说明替代可执行验证。阶段 11 的运行材料可以使用生成脚本重建，`run-record.json` 中的 `actual_cli_execution=true` 和退出码用于区分实际执行与文档描述。

## 边界

项目提供真实模型适配入口，但自动测试不发送真实请求；默认离线 Mock 只能验证工程流程，不能证明真实模型的决策效果或账号 API 可用性。
